## 问题 1：Mockito varargs 匹配器使用错误

- 文件：`src/test/java/com/example/backend/service/BaseServiceUnitTest.java`
- 用例：`beginRedisUuidStoresContentWithGeneratedKeyAndConfiguredTimeout`
- 现象：`InvalidUseOfMatchersException`
- 原因：`RedisHelper.hasString(String, Object...)` 是 varargs 方法，测试中混用了原始字符串和 `anyString()` 匹配器。
- 修复：把模板参数也改为 `eq("unit:%s")`，保证所有参数都使用 matcher。

## 问题 2：非图片文件的实际失败点早于图片类型校验

- 文件：`src/test/java/com/example/backend/service/FileServiceUnitTest.java`
- 用例：`uploadTempImageRejectsNonImageContentBeforeRedisWrite`
- 现象：预计消息为 `exception.invalidate.file.image_only`，实际为 `exception.invalidate.file.unsupported_media`。
- 原因：`FileUtils.getFileExtensionAndType` 会先拒绝不支持的 MIME 类型，文本文件不会进入图片专用校验。
- 修复：调整预期为 `exception.invalidate.file.unsupported_media`，仍验证不会写 Redis。

## 问题 3：JWT 拉黑测试的 Redis stub 时序不正确

- 文件：`src/test/java/com/example/backend/util/JwtAndSecurityUnitTest.java`
- 用例：`invalidatedAccessTokenIsStoredUntilJwtExpirationAndThenRejected`
- 现象：拉黑后 token 仍被判定有效。
- 原因：`invalidateAccessToken` 不调用 `hasKey`，`validateAccessToken` 第一次调用 `hasKey` 时拿到了 stub 的第一个返回值 `false`。
- 修复：拉黑完成后把 `hasKey` 设为 `true`，模拟 Redis 中已存在拉黑键。

## 问题 4：WORKER 角色被映射为 ROLE_ADMIN

- 文件：`src/main/java/com/example/backend/entity/property/UserRole.java`
- 用例：`customUserDetailsMapsBitmaskRolesToSpringAuthorities`
- 现象：`WORKER` 用户 authority 中包含 `ROLE_ADMIN`。
- 原因：`ADMIN` 的 `matchMask` 为 `0x0`，`(mask & 0) == 0` 对任意角色都成立。
- 影响：任何登录用户在 Spring Security authority 中都会被授予 `ROLE_ADMIN`，存在越权风险。
- 修复：将 `ADMIN` 的 `matchMask` 从 `0x0` 改为 `0x1F`，只有拥有完整权限掩码的用户才匹配管理员角色。
